# Secured sample routing workflow — KAN-19 / KAN-15

1 November 2026. This extends the real cargo browser workflow. KAN-19 remains In Progress for authenticated live tracking/WebSocket lifecycle and the legacy mobile logger. Full KAN-15/KAN-18 and KAN-14 acceptance remain open.

## Functional behavior

Operator and Administrator can open Assign route from cargo details, inspect sample candidates, select one and save its itinerary. Reader can view the resulting itinerary and routing status but cannot request candidates or assign/reroute. Anonymous users must log in for protected pages; anonymous API requests return401 and Reader mutation requests return403.

Candidates are generated by the original demonstration planner with random intermediate stops and voyage identifiers. This increment restores its existing application workflow; it does not implement a carrier timetable optimizer or promise the shortest feasible voyage. The application filters generated routes against origin/destination/deadline. A cargo whose deadline cannot be met shows a controlled no-candidates message with no assignment button.

The selected index refers only to the server-held candidates in that Faces view; the client cannot submit arbitrary leg DTOs. Missing/unknown selections, forged Reader submissions and missing CSRF are denied. On assignment, the service reloads current cargo and checks the itinerary against its current specification. If another view has already changed destination, an old route is rejected with a request-fresh-routes message. This verifies committed stale state, not race-free concurrent updates; optimistic locking/concurrency still requires later work.

Both first assignment and rerouting persist the selected voyage/location/time sequence. Details expose the full itinerary; tables scroll within their container on a narrow viewport. ROUTED, MISROUTED and NOT_ROUTED are displayed distinctly.

## Identity and internal HTTP boundary

Human routing page/API access remains limited to approved Operator/Administrator sessions. The internal ExternalRoutingService retains a separate HTTP call to GraphTraversalService using a dedicated WildFly ApplicationRealm account with only RoutingService role. No human password, browser cookie, claimed role or Administrator credential is forwarded.

RoutingAuthenticationFilter accepts a preemptive Basic credential only on the exact graph endpoint. It delegates credential checking to Servlet request.login against the server realm, verifies RoutingService membership, and logs out/invalidates any created session afterward. Basic headers on other paths do not authenticate callers. Combining an already authenticated session with Basic is rejected, as are malformed/duplicate/oversized headers. The EJB graph service also checks roles; the HTTP manifest grants no other application route to RoutingService.

The client accepts only the fixed loopback localhost/127.0.0.1 port8080 graph URL with no userinfo/query/fragment, applies timeouts, disables RESTEasy redirects and closes the client on bean destruction. This is a single-server lab topology; remote service/TLS/credential-rotation deployment is not implemented. Provision the password outside Git/images via the cargo.routing.credentials file property. No missing-credential fallback or human-identity reuse exists.

The disposable runtime harness generates a separate per-run routing password, realm digest/role and private read-only client properties. Three private files are cleaned even after partial initialization; the new regression injects a partially written routing secret failure. Human browser fixtures receive only their three human accounts. No credential values, Authorization headers, cookies, traces or browser state are published.

## Persistence correction

Actual browser assignment exposed Hibernate orphan-delete wrapper loss when Cargo replaced its embedded itinerary. Cargo now updates its aggregate-owned leg collection in place, with a defensive input copy; the supplied equivalent route value drives the immediate delivery transition. Itinerary getters remain unmodifiable and replacement is package-private. This preserves the existing domain status assertions while allowing managed collection ownership to survive assignment/rerouting. Real initial/replacement route readback covers the failure, but independent physical orphan-row/database migration checks are not claimed.

The first failed assignment report and cause are retained under notes/evidence/kan-19-routing/first-assignment-failure.
